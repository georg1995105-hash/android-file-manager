# Передача задач между агентами — протокол v1

Цель: новый агент продолжает работу с последнего **подтверждённого** шага, а не по пересказу чата или догадке модели. Хранилище состояния — GitHub Issue/PR/коммиты/CI. Никаких отдельных серверов или платной индексирующей базы.

## Источники истины (в таком порядке)

1. **Живое состояние:** открытые Issue, PR, head SHA и текущие результаты GitHub Actions. При смене head SHA прежние проверки нельзя переносить автоматически.
2. **Реальная реализация:** исходники на целевой ветке и тесты, а не README или обещания в PR.
3. **Правила:** AGENTS.md, требования, архитектура, ADR из Git. Документ от старой версии может быть только исторической справкой.
4. **История решений:** комментарии в Issue/PR, старые коммиты. Они не отменяют свежие подтверждённые данные.

Поиск/RAG/Graphify может ускорить чтение, но **не** является источником статуса или доказательством прохождения тестов. Указывать ветку, SHA и дату каждого важного вывода.

## Единица работы

- **Issue** — проблема, критерии приёмки и ограничения. Не переписывать симптомы в общее «сделано».
- **Отдельный PR** — реализация + живой handoff в описании. Один PR на конкретную задачу, не смешивать несвязанные правки.
- **Коммит** — точная версия кода. **CI run** — результаты автоматических проверок для этого коммита. **Устройство/production** — отдельное подтверждение, никогда не подменять их успешной сборкой.
- При остановке, смене агента или блокировке актуализировать PR: «Выполнено», «Подтверждено», «Не проверено», «Следующий шаг», «Риски и секреты». Никаких параллельных устаревающих файлов текущего состояния.
- Следующий агент сначала сверяет branch/head, связанный Issue, PR, CI, затем воспроизводит **только** непроверенное. Не повторять дорогую диагностику, если результаты уже действительны для того же кода и среды.
- Если продукт меняется после подтверждения, сбросить статусы предыдущих проверок на `working` и `not_run` до нового результата. При конфликте данных считать статус непроверенным, а не «готовым».

## Машиночитаемый handoff

Каждый новый PR, использующий протокол, содержит комментарий:

```text
<!-- agent-handoff:v1
issue: #123
phase: working
head: pending
ci: not_run
device: not_tested
-->
```

- `phase`: `working`, `blocked`, `ready`.
- `head`: `pending` до проверки или **полный SHA текущей головы PR**.
- `ci`: `not_run` либо `passed https://github.com/owner/repo/actions/runs/123`, либо `failed <URL>`.
- `device`: `not_tested`, `passed`, `failed`, `not_applicable`. Для `not_applicable` описать причину в «Не проверено»/«Подтверждено».
- `ready` допускается лишь с точным `head`, ссылкой на успешный CI и результатом устройства `passed` либо обоснованным `not_applicable`. **Поле не проверяет правдивость результата:** ссылку, обязательные тесты и выводы проверяет инженер отдельно.
- При новом коммите изменить head и снова указать реальные результаты проверок. Старые ссылки можно оставлять в истории PR, но не как доказательство нового head.
- Существующие PR без маркера не блокируются. Не изменять их автоматически.

CI `.github/workflows/agent-handoff.yml` работает только для PR с маркером, в режиме чтения (`contents:read`, `actions:read`), не исполняет текст PR. Для `ready` дополнительно запрашивает GitHub API и сверяет, что указанный прогон **завершился успешно на этом head SHA**. Это не заменяет оценку охвата проверок и ручное тестирование. Тесты — `python3 -m unittest discover -s scripts -p 'test_agent_handoff.py' -v`. Локальная проверка с переменными `PR_BODY`, `PR_HEAD_SHA`, `GH_REPO`.

## Минимальная эффективная процедура

1. Уточнить цель, прочитать Issue/PR и только относящиеся к задаче файлы. Не скармливать агенту весь репозиторий.
2. Найти одну причину и зависимости (поиск кода, при сложных связях — локальный индекс Graphify; не включать облачный LLM-индексатор для приватных данных).
3. Сделать минимальное изменение в своей ветке, запустить релевантные тесты.
4. Записать commit SHA, **ссылку на реальный прогон**, что именно прошло, что упало и что не запускалось.
5. После проверок на нужных устройствах/средах закрыть критерии Issue. Merge, подпись и релиз — самостоятельные этапы с собственным подтверждением.

## Безопасность

Публичные репозитории содержат **только** общие схемы и очищенные документы. Не сохранять сюда серверные IP, доступы, bearer-токены, закрытые URL подписок/зеркал, cookie, SSH-ключи, ключи подписи, выводы команд с секретами и приватные конфиги. Не отправлять эти сведения в облачные базы знаний или Graphify с внешним LLM. Живые секреты — в защищённых хранилищах, а не в графе знаний. Отдельные разрешения и инструментальная авторизация обязательны для боевой инфраструктуры; документы не дают агенту права делать production-правки.

## Границы

Это **система воспроизводимого состояния**, не постоянный автономный процесс и не автоматически обновляемая база RAG. Она работает только когда агент дисциплинированно обновляет PR/Issue. Для ранее открытых PR и устройств нельзя выдумывать старые результаты. Не создавать отдельную БД/GraphRAG, пока поиск в Git и связанная история Issue/PR достаточны.
