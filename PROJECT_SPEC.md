Ты — исполнитель нового **полностью независимого личного проекта**. Это Android APK **для самого владельца, не для продажи/публикации**. Передача этого ТЗ вместе с макетом на запуск **означает разрешение только на создание одного нового приватного GitHub-репозитория** в доступном владельцу аккаунте для этого Android-проекта и на push собственных, проверенных коммитов туда. Выбери свободное нейтральное имя репозитория вроде `personal-android-file-manager`; **не используй существующий `workspace`, PHANTOM, GHOST и любые чужие репозитории**. Верифицируй, что видимость `PRIVATE`, прежде чем отправлять код. Публикация в публичном репозитории запрещена. Это не даёт разрешения удалять/переименовывать существующие репозитории, менять их права, секреты, настройки аккаунта или изменять другие проекты.

Если GitHub недоступен или создавать репозиторий в текущей среде нельзя — не требуй токен в чате и не застревай на этом: веди новый **локальный Git** и подготовь скачиваемый архив исходников/проверенных коммитов как резервный долговечный путь. Укажи, что *push не подтверждён*. При наличии доступного GitHub проверь `git remote`, `git push` и удалённый commit SHA; «локально закоммичено» не означает «надёжно сохранено». Репозиторий строго для исходников и документации, без личных файлов с телефона и без ключей подписи.

Работай **последовательно небольшими законченными этапами**, чтобы лимит Codex мог закончиться в любой момент без потери достигнутого. Не пытайся реализовать все функции в одной сессии. При отсутствии Android SDK/эмулятора честно указывай границы проверки; никакого фиктивного PASS и заявления «APK готов», если сборки нет.

Не устраивай многократных широких аудитов. На каждом этапе: нужный код → целевая проверка → сборка (если среда позволяет) → Git-коммит исправного состояния → короткое обновление `PROJECT_STATUS.md` → следующий этап в рамках остатка лимита. Работающий код без причины не переписывай.

**Начни с ЭТАПА 1.** После каждого действительно законченного этапа сохраняй код и APK (если собран), обновляй статус и **продолжай следующий этап самостоятельно в рамках оставшегося лимита**, если не нужен физический тест/доступ владельца. Не останавливайся ради очередного красивого плана или вопроса «продолжать?». Когда нужен тест на vivo, сообщи одним коротким сообщением конкретные действия владельца, но можешь параллельно выполнять безопасные автономные шаги. Если нужно выбрать несущественную реализацию — решай самостоятельно. Опасные, необратимые действия с личными файлами, выдача секретов, передача данных третьим лицам — не импровизируй.

## 1. Технологии

- **Нативный Android:** Kotlin, Jetpack Compose, Material 3 / адаптивные компоненты AndroidX.
- Актуальные на момент работы **стабильные** Android SDK, Android Gradle Plugin, Gradle и Kotlin — подбирай совместимые версии, не бери экспериментальные версии без необходимости.
- Архитектура простая и тестируемая: UI → ViewModel/state → репозитории файлов/медиа/настроек. Без избыточной многомодульности.
- **DataStore** — порядок иконок, нижних вкладок, визуальные настройки; **Room/SQLite** — собственные заметки, ссылки и прочие структурированные данные, если они реализуются.
- **MediaStore + Storage Access Framework (SAF)** и уместные Android API для просмотра файлов. Дополнительное разрешение «доступ ко всем файлам» запрашивать только при реальной необходимости полноценного файлового менеджера, с понятным объяснением и корректной работой при отказе. Без root.
- **AndroidX Media3/ExoPlayer** — видео; AndroidX/совместимая библиотека обработки изображений для фото.
- Локальная работа без VPS, регистрации, аналитики и трекеров. Сеть по умолчанию не нужна; не запрашивать `INTERNET`, пока не появится конкретная разрешённая функция, которой это действительно требуется.
- Целевая проверка — на реальном смартфоне владельца (современный Android, в том числе Android 16). Корректная работа на разных размерах дисплея и системных масштабах текста.

### Основное устройство, совместимость и сборки — обязательные требования с первого этапа

- **Личный основной смартфон владельца: vivo X300 Pro, Android 16, 64-битная ARM-архитектура (`arm64-v8a`).** Его экран, реальные системные разрешения, установщик и работа с файлами — главная цель проверки. Не считать поведение эмулятора доказательством работы на этом устройстве.
- **Основной выпуск APK — для ARM64 (или единый APK без ABI-зависимостей, если нативных `.so` нет).** Подготовить конфигурацию сборки так, чтобы при наличии собственных/сторонних нативных (`.so`) библиотек выпускать вариант `arm64-v8a`, без ненужных для владельца архитектур. Если в первом этапе все зависимости JVM/Kotlin и ABI-специфичных библиотек нет, не вводить искусственные ABI-фильтры и не усложнять сборку ради вида «оптимизации».
- **Возможность универсального APK** из тех же исходников сохранить с первого дня; он должен включать все необходимые поддерживаемые ABI только при наличии нативных библиотек. «Универсальный» не означает, что APK заработает на *любой* версии Android или на устройстве без нужных аппаратных возможностей. Не делать отдельную кодовую базу.
- При интеграции нативного архиватора и других библиотек проверить **совместимость с размером страниц памяти 16 КБ** (включая выравнивание/упаковку нативных библиотек) для современных ARM64 Android; проверить используемые `.so`, а не предполагать совместимость по названию архитектуры. Предпочитать актуальные поддерживаемые зависимости.
- Подбирать `minSdk`, `targetSdk`, зависимости и разрешения на основе совместимости с **реальным Android 16** и доступной системы сборки. Не занижать `targetSdk` искусственно ради обхода ограничений Android, не обещать полный доступ ко всем директориям.
- UI адаптировать к плотности, вырезам, жестовой навигации и размеру шрифта: дизайн-макет не задаёт физические пиксели. Ландшафтный поворот для медиапросмотра только по явной команде пользователя; системный автоповорот не должен неожиданно менять просмотр.

## 2. Главный UX и внешний вид

Ориентир: простота File Manager+, но с более удобным управлением одной рукой. Тёмная аккуратная тема с умеренными цветовыми акцентами, без рекламных баннеров и визуального шума.

- Главная: карточка памяти устройства, **крупные плитки категорий**, ниже — **недавно добавленные/загруженные файлы** (свежие выше), понятное меню действий с файлом.
- Категории: «Загрузки», «Новые», «Фото», «Видео», «Документы», «Архивы», «Приложения», «Заметки», «Ссылки», «Избранное», «Файлы». Возможны другие полезные категории, но **не добавлять их без причины**. «На ТВ» и передача файлов на ТВ — только отложенная идея, не часть первой версии. **Трансляция/воспроизведение видео на телевизоре по Wi-Fi исключена из объёма проекта.**
- **ВСЕ главные плитки настраиваются:** скрыть/показать, перетаскиванием менять местами, выбирать новый значок **и при желании цвет** из встроенного набора; порядок, выбор и название раздела (если это пользовательский ярлык) сохранять. Никакого самовольного изменения системных категорий.
- По желанию предусмотреть **собственную картинку иконки (PNG/WebP через системный выбор файла)** как позднее улучшение персонализации: безопасно копировать выбранное изображение в собственные данные приложения, учитывать потерю доступа к исходному URI, разумно ограничивать размер и декодирование. Не блокировать первый APK этой опцией. Не предлагать удалённые наборы иконок.
- **ВСЕ нижние вкладки настраиваются:** добавить/убрать, порядок, заменить значок и при желании цвет; комфортно показывать до 5 вкладок, остальные разделы доступны с главного экрана. Настройка свайпом/перетаскиванием, при необходимости альтернативные стрелки для доступности. Не оставлять приложение без доступной навигации.
- Поиск, управление и основные действия расположить в **нижней зоне досягаемости большого пальца**. Верх не должен содержать единственные часто используемые кнопки. При открытой клавиатуре не закрывать список файлов; корректно учитывать жестовую системную навигацию.
- **Принцип без лишнего:** не дублировать одно и то же действие несколькими большими кнопками; плотность информации — умеренная; лёгкий возврат назад, читаемые подписи без обрезки, адекватные области нажатия для пальца.
- Главная должна сохранять понятность File Manager+: плитки «Загрузки / Новое / Фото / Видео / Документы / Архивы / Приложения» и список недавних файлов. Это **оригинальный UI по согласованному макету**, не копирование чужих ресурсов/брендинга.
- В каждой категории — осмысленное пустое состояние; понятный отказ разрешений; русский текст без обрезания подписей; светлая тема — не обязательна для первого APK.
- Не фиксировать физические пиксели: адаптивные размеры, плотности, safe insets, системная навигация, размеры шрифта. Не допускать наложений интерфейса при клавиатуре и смене размера окна.
- Любая кнопка на рабочем экране должна делать заявленное действие; никаких вводящих в заблуждение заглушек.

## 3. Работа с файлами

### Основные операции

- Просмотр доступных файлов и папок, создание папки, сортировки, выбор одного или нескольких файлов, поиск по доступным хранилищам, сведения о файле.
- Копирование, перемещение, переименование, отправка через системный Android Sharesheet с корректными `content://` URI и временными правами доступа. Реализовать после безопасного ядра просмотра.
- Удаление только с предохранителями: подтверждение для необратимых действий, возможность восстановления там, где это технически поддерживается. Не заявлять универсальную «корзину» без надёжной реализации для конкретного типа хранилища.
- Перед изменяющими операциями проверять наличие места, источник и назначение; избегать перезаписи без явного выбора пользователя. Не удалять оригинал до успешного и проверенного завершения переноса. При сбоях оставлять исходный файл нетронутым и показывать понятную ошибку.
- Длинные операции — не блокировать UI; прогресс, отмена, обработка нехватки места и отказа доступа.

### Недавние файлы

- «Новое» — один из самых важных экранов. По возможности первыми должны быть **файлы, недавно добавленные/загруженные**, а не файлы с произвольной датой изменения внутри архива.
- Не путать `date added`, `date modified`, дату создания и время последнего доступа. Использовать подходящие поля Android MediaStore/Downloads, там где доступны; дать честный fallback и понятное название сортировки. Универсальную точную дату скачивания для каждого файла Android не гарантирует.
- После возвращения в приложение обновлять список без лишней кнопки «Обновить», не сканируя бесконтрольно весь накопитель.
- Практические расширения: `.md`, `.txt`, `.json`, `.yaml/.yml`, `.xml`, `.csv`, `.log`, `.pdf`, `.zip`, `.7z`, `.rar`, `.apk`, `.apks`, фото, видео и любые другие доступные файлы. Для текстовых форматов нужен простой **встроенный просмотр** с корректной кодировкой, ограничениями размера и копированием текста; PDF — встроенный просмотр только если есть надёжный простой вариант, иначе открытие через установленное приложение без лишних подтверждений. Неизвестный формат всё равно можно увидеть, копировать и переслать.
- **Не обещать изменить системный Android-пикер внутри ChatGPT и других приложений.** Наш менеджер не может заставить чужой системный выбор файлов сортировать по своим правилам; вместо этого дать удобное открытие и **«Поделиться» прямо из нашего списка новых файлов**, если целевое приложение принимает такой тип отправки.
- Удобные базовые сценарии: открыть, выбрать несколько, поделиться, скопировать, переместить, переименовать, создать папку, увидеть реальный путь/URI и размер, сортировка по имени/дате/размеру/типу, при наличии доступа — скрытые файлы. Не пытаться читать каталоги, заблокированные Android.

## 4. Фото и видео — встроенный удобный просмотр

### Фотографии

- Открытие внутри приложения, без обязательного перехода в стороннюю галерею.
- Полноразмерный просмотр, перелистывание соседних изображений, увеличение/уменьшение жестами, двойное касание для масштаба, свайп между фото, скрытие/показ UI касанием.
- Сохранение реальных пропорций и корректной ориентации фотографии по её метаданным; не обрезать кадр неожиданно.
- Раздел «Фото» может показывать сетку миниатюр, но **не превращать приложение в отдельный сложный продукт-галерею**. Не вводить облачные альбомы, фоторедактор, искусственные функции и автоимпорт.

### Видеоплеер

- **Media3/ExoPlayer** для распространённых видео; целевая возможность — **4K до 60 FPS** на телефонах с подходящим аппаратным декодированием. Не обещать воспроизведение абсолютно всех кодеков или аппаратно недоступного 4K60. 8K не требуется.
- Приоритетные контейнеры: MP4, MKV, WebM, MOV, распространённые кодеки H.264/H.265/VP9/AV1 в пределах реальной поддержки устройства. Не перекодировать видео автоматически; честно показывать ошибку неподдерживаемого формата.
- Двойной тап **слева −10 секунд**, **справа +10 секунд**; не рисовать отдельные круглые кнопки «−10/+10».
- Одно касание показывает/скрывает контролы; в нижней области — минимум необходимого: пауза/воспроизведение, seekbar/время, ручное разворачивание/сворачивание. Дополнительные параметры вроде скорости воспроизведения и субтитров — только в компактном меню; никаких навязчивых overlay.
- При просмотре локального видео: корректно обрабатывать задержку seek, поведение аудиофокуса/звонка, отсутствие поддерживаемого декодера, расход батареи и освобождение плеера после выхода. Поддержку отдельного субтитра `.srt`/WebVTT/ASS можно добавлять при реальной совместимости; не обещать универсальное воспроизведение. Запоминание позиции последнего видео — опциональное удобство с локальным хранением без передачи наружу.
- **НЕТ автоматического поворота** фото или видео от датчика ориентации телефона. Обычный просмотр по умолчанию, переход на полный экран только по явной кнопке. В полноэкранном режиме — видимая, удобная кнопка возврата. Если нужен ландшафтный просмотр, поворачивать только по отдельной пользовательской команде, не по датчику.
- Фоновое воспроизведение, потоковое вещание на ТВ, сложные редакторы и медиабиблиотека не нужны.

## 5. Архивы

Впоследствии встроить архиватор так, чтобы пользователь не искал отдельные приложения для обычных архивов.

- Распаковка/просмотр **ZIP, 7z, RAR/RAR5, TAR, TAR.GZ, TAR.XZ, TAR.ZST, GZ, XZ, ZST** при наличии совместимого проверенного движка; пароли, выборочная распаковка, многотомные `.part1.rar`, `.7z.001`, `.z01` — с тестами. Создание минимум ZIP и при надёжной реализации 7z. **ZIPX** рассмотреть и явно указать поддерживаемые методы сжатия: расширение файла само по себе не гарантирует чтение. Позднее, только если выбранная библиотека корректно поддерживает, можно добавить просмотр/извлечение **ISO, CAB, DEB, RPM** без выполнения программ внутри них. Не считать эти редкие форматы обязательным условием первого выпуска.
- **RAR создавать не требуется**: отдельные лицензионные ограничения; допустимо только чтение с соблюдением лицензий.
- Архивный движок выбирать после анализа API, поддерживаемых кодеков, размеров APK, сопровождения и лицензий. Не включать непроверенные бинарные сборки.
- Строгая защита от `../` path traversal/Zip Slip, абсолютных путей, ссылок за пределы назначения, переполнения хранилища и декомпрессионных бомб. Безопасное поведение при повреждённом/зашифрованном архиве.
- Если формат ещё не реализован, открыть его через доступное внешнее приложение — лучше честный fallback, чем ложное обещание.

## 6. Раздел «Приложения» и установочные файлы

- Список доступных установленных приложений и локальных APK/пакетов; запуск установленного приложения.
- Экспорт установочного пакета, сохранение и отправка мессенджером/другим приложениям.
- Учитывать **split APK**: один `base.apk` не всегда пригоден для переустановки. Для таких приложений требуется экспорт всех нужных частей и формирование корректного набора; обозначать ограничения и проверять воспроизводимость на совместимом Android.
- Локальные APK можно открывать в **штатном системном установщике** с подтверждением пользователя; никакой тайной установки, root и обхода защиты Android. Сторонние `.apks`/`.xapk` — только после отдельной проверки структуры и безопасного решения для установки.
- НЕ извлекать личные данные приложений: экспорт APK ≠ бэкап данных аккаунтов. Сохранять корректную подпись исходных APK без модификации пакетов; проверять размер/целостность экспортированного набора и честно предупреждать, что переустановка может зависеть от версии Android, лицензирования, устройства и набора split-файлов.
- Список установленных приложений получать через Android PackageManager в рамках разрешённой видимости. При необходимости для действительно полного списка оценить `QUERY_ALL_PACKAGES`, поскольку приложение **личное и распространяется вне Play**; тем не менее доступ должен соответствовать цели и не собирать лишние данные. Никакой скрытой телеметрии.
- Режим работы с уже скачанными `.apk`: предпросмотр имени/версии/иконки, отправка и запуск штатного установщика по согласию пользователя; не обходить системную проверку/Play Protect и запреты Android.

## 7. Личные разделы

- **«Заметки»**: минимальный локальный редактор текста с автосохранением, понятным экспортом и резервной копией.
- **«Ссылки»**: название, URL, быстрый поиск, открытие в браузере, копирование, экспорт. Без подключения к аккаунтам и без удалённого сервера.
- **«Избранное»**: избранные папки/файлы с корректной реакцией на перемещение или удаление источника.
- Не заставлять пользователя видеть эти разделы: все скрываемые и переставляемые плитки/вкладки.
- Для данных, существующих только внутри приложения, нужен понятный **ручной экспорт и импорт**, чтобы удаление/сбой приложения не уничтожили всё без возможности восстановления. Android-автобэкап не считать единственной гарантией.
- Собственные локальные заметки и ссылки не передавать в сеть, не индексировать внешними сервисами. Проверить правила системного Android backup/data extraction: **не допустить незаметного незашифрованного облачного сохранения личных данных по умолчанию**; выбрать и задокументировать подходящие `dataExtractionRules`/`fullBackupContent` или отключить неуправляемый системный бэкап с предоставлением явного экспорта владельцу.

### Резервное копирование и восстановление (обязательная функция позднего этапа, НЕ блокер первого APK)

**Цель:** личные данные и индивидуальные настройки можно самостоятельно перенести на другой смартфон или вернуть после переустановки. **VPS, аккаунт и собственный облачный сервер не нужны.** Работать офлайн; выбранное пользователем внешнее хранилище — опция.

- Раздел настроек **«Резервные копии»**: «Создать копию», «Восстановить», «Автокопирование» (выключено по умолчанию), дата/размер последней *успешной и проверенной* копии, состояние ошибок. Нельзя показывать «сохранено», если операция не завершилась.
- В состав **небольшой резервной копии приложения** включить заметки, ссылки, избранное, настройки, расположение и иконки плиток и вкладок, прочие собственные данные приложения. **Не копировать автоматически** все фото, видео, загруженные APK, архивы и папки пользователя: это его обычные файлы, а не база нашего приложения. Для избранных файлов сохранять ссылки/метаданные, а не содержимое; после восстановления корректно показывать недоступные пути.
- **Ручной экспорт:** один переносимый файл резервной копии с версией формата и метаданными, сохранение через системный Android Storage Access Framework («Сохранить как…»). Пользователь может выбрать папку телефона, USB-носитель либо провайдер облачного хранилища, если он установлен и интегрирован в системный выбор файлов. Не требовать собственного сервера.
- **Ручное восстановление:** выбрать файл через системный диалог, проверить его формат/версию/целостность/размер, показать понятное предупреждение, что будет восстановлено и какие текущие данные могут замениться; запросить подтверждение. Не перезаписывать рабочую базу до успешной проверки, подготовить безопасную замену с возможностью отката при ошибке. Обрабатывать более старые поддерживаемые версии схемы. Повреждённая копия не должна ломать приложение.
- **Защита личных данных:** предусмотреть опционально **шифрованный паролем переносимый экспорт** с проверенной схемой аутентифицированного шифрования (например, AES-GCM + надёжное выведение ключа из пароля). Не хранить пароль внутри файла, логов или исходного кода. Android Keystore можно использовать для локального секрета, **но не вместо переносимого пароля**: привязанный к устройству ключ после смены телефона может быть недоступен. При утрате пароля зашифрованную копию восстановить нельзя; сообщать об этом заранее. До внедрения шифрования не обозначать обычный архив как защищённый.
- **Автокопирование — отдельный последующий шаг:** по согласию пользователя, например ежедневно или еженедельно, в **заранее выбранную через SAF папку**. Использовать системный планировщик фоновых работ (WorkManager или актуальный аналог); Android не гарантирует запуск строго в заданную минуту. Сохранять устойчивое разрешение на выбранную папку, учитывать его отзыв, недоступность носителя, нехватку места. При ошибке показывать её в интерфейсе; не заявлять, что копия сделана.
- Ограничивать число автоматически сохранённых версий разумной настройкой (например, последние 7), но удалять только подтверждённые старые резервные файлы **нашего приложения** и только после успешного создания новой копии. Не удалять произвольные файлы в выбранной папке.
- Для проверки восстановления достаточно отдельных целевых тестов: успешный перенос на чистую установку, испорченная/неподдерживаемая копия, неверный пароль, отказ доступа, нехватка места, восстановление после частичного сбоя. Не подменять проверку простой записью файла. Восстановление по умолчанию **не затрагивает обычные документы, фото и видео владельца**.
- Безопасность формата: переносимая структура с явной версией, manifest/контрольными суммами, строгими пределами размеров/количества записей, проверкой формата до записи в БД, атомарным применением (транзакция или аналог), rollback при ошибке. Шифрование только с аутентификацией; не изобретать собственный криптопротокол. Формат `backup` не должен содержать постоянный release-ключ подписи APK.
- **Подчеркнуть пределы защиты:** копия, оставленная лишь на том же телефоне, не спасёт при потере или поломке устройства. Советовать хотя бы одну отдельную копию на ПК/USB/личном облаке. Не обещать автоматическую синхронизацию между телефонами: она в проект не входит.

## 8. Безопасность, надёжность и установка APK

- Приложение устанавливается **лично пользователем** как APK; Google Play и RuStore не нужны. Никакой «публикации», публичного сайта, VPS или платного сервиса. Всё должно быть применимо к одному Android-смартфону.
- **Безопасный старт:** тесты файловых операций только на автоматически созданных тестовых каталогах/копиях. Не использовать реальные документы, архивы, фото или данные приложений владельца в CI/облачных тестах и не загружать их в репозиторий/LLM-подсказки.
- Управлять разрешениями по принципу наименьших привилегий; приложение должно корректно объяснять расширенное разрешение на управление общими файлами и не путать его с root. Android 11+ ограничивает доступ к `/Android/data` и `/Android/obb` даже при широком разрешении; это должно быть честно отражено в интерфейсе.
- Защитить любой импорт, URI и архив от непредвиденных путей, внешних `content://` провайдеров, чрезмерного потребления RAM, утечки файлов через слишком широкие разрешения FileProvider. Никаких экспортируемых компонентов Android без явной потребности и должного контроля доступа.
- Для копирования/переноса/восстановления: потоковая работа, промежуточные файлы в контролируемом каталоге, финализация только после успеха, обработка отмены и нехватки места; не обещать атомарность для произвольных SAF-провайдеров без её проверки.
- Не использовать root, скрытые сетевые соединения, трекеры, агрессивный сбор сведений о других приложениях или установку без ведома пользователя.
- Запрашивать только необходимые разрешения; ясно объяснять их назначение; учитывать ограничения Android 13–16.
- Любая обработка файлов — из недоверенного ввода, в том числе архивы и контент-провайдеры. Без исполнения кода из архивов.
- Стабильность при поворотах/смене масштаба системного UI, нехватке памяти, больших файлах и отменённых системных диалогах.
- **Подпись APK и обновление:** техническая debug-сборка допустима только для временных испытаний. **До установки первой постоянной пользовательской версии** настроить стабильную release-подпись и сохранить ключ под контролем владельца. Debug APK, подписанный другим ключом, **нельзя обещать обновить поверх** постоянного release APK без удаления: предупреди владельца до установки. Не хранить release-keystore или пароли в Git, выдаваемом архиве исходников, логах и временных облачных средах. Подготовь воспроизводимую процедуру локального подписания/защищённой сборки и понятный однократный шаг по созданию ключа, если у владельца его ещё нет. Не создавать «секретный» ключ в месте, где владелец не сможет его безопасно забрать и сохранить отдельно; не обещать бесшовные обновления, пока подпись не подготовлена. Сделать резервную копию ключа в отдельном защищённом месте.
- Никаких секретов, keystore, паролей, токенов и приватных файлов пользователя в репозитории. Проверить `.gitignore`.
- Реальные установки, разрешения, открытие файлов и обновления APK требуют проверки **на телефоне**, а не только на эмуляторе/CI. Владелец сам разрешает установку из источника, если Android запросит это; безопасность Android не отключать, никаких инструкций по обходу встроенных защит.
- **Подписывание в облаке без утечки секрета:** не создавать единственный незаменимый release-keystore в эфемерной среде, если отсутствует проверенный способ безопасно передать его владельцу и сделать отдельную резервную копию. Не отправлять ключ или пароли обычным сообщением, не фиксировать в Git, артефактах публичной CI или логах. Подготовить безопасную однократную процедуру и конфигурацию подписи, не блокируя написание кода. Если владелец ещё не обеспечил сохранность ключа, выдавай честно маркированный `DEBUG/TEST APK`, предупреди о невозможности гарантировать его обновление поверх будущего release без смены подписи. Для **постоянной первой установки** нужен надёжно сохранённый release-ключ.

### Версии и обновления поверх установленного APK — зафиксировать ДО первой постоянной установки

- Назначить и документировать **неизменный `applicationId`** приложения; не менять его при последующих сборках, поскольку Android иначе воспримет программу как другое приложение. Имя, иконку и отображаемые подписи при этом можно менять.
- Вести `versionName` (например, `0.1.0` → `0.1.1` → `0.2.0`) и **строго возрастающий `versionCode`** для каждого устанавливаемого обновления. Номера менять в единственном понятном месте Gradle-конфигурации; записывать их в `PROJECT_STATUS.md`/истории выпусков.
- Для обновлений одного установленного приложения обеспечивать **тот же `applicationId` + совместимую цифровую подпись + подходящий `versionCode` + совместимость устройства**. Для обычного личного проекта использовать один и тот же сохранённый release-ключ. Запретить нечаянную смену ключа или package ID после начала реального использования.
- Данные в **DataStore/Room** и пользовательские файлы должны сохраняться при штатной установке нового APK поверх старого. Изменения схем Room делать только с продуманными миграциями; не использовать destructive migration ради удобства. Отдельно проверить переход между двумя версиями **без удаления приложения**, убедиться, что настройки, плитки, заметки и ссылки (когда реализованы) остались целыми.
- Если после внедрения нативных библиотек меняется набор поддерживаемых ABI (ARM64 ↔ universal), обновления должны оставаться совместимыми с основным vivo и его установщиком. Не смешивать разные release-ключи между вариантами сборок.
- Перед выпуском очередного APK по возможности выполнить **тест обновления поверх старого установленного тестового APK** с той же подписью (`0.1.0` → `0.1.1`) и убедиться, что DataStore/Room переживают переход; на vivo этот тест подтверждает только пользователь. Не считать чистую установку тестом обновления. Вести краткий `CHANGELOG.md`.
- Публикация в магазине, автообновления через Интернет и отдельный VPS **не требуются**. Владелец сам получает и устанавливает подписанную новую версию. По завершении каждого выпуска отдавать APK, точный `versionName/versionCode`, контрольную сумму SHA-256 и краткое описание изменений; фактическую установку и сохранность данных подтверждает владелец на устройстве.

## 9. Этапы разработки и критерии завершения

### ЭТАП 1 — первый рабочий устанавливаемый APK (начинать с него)

1. Создать отдельный Android-проект и локальный Git-репозиторий.
2. Сделать главный экран по макету: карточка памяти, категории, действительно работающий список файлов; нижняя панель.
3. Реализовать изменение порядка/набора/иконок главных плиток и нижних вкладок, сохранение в DataStore.
4. Реализовать просмотр файлов и папок через доступные API и корректные сценарии разрешений.
5. Экран «Новое»: реальные данные, обоснованная сортировка, автоматическое обновление по возврату в приложение.
6. Поиск по доступным данным, просмотр сведений, системное «Поделиться» для файлов.
7. Базовый встроенный просмотр изображений.
8. Собрать APK; выполнить только необходимые unit/build/smoke проверки. Сохранить исходники и результат сборки в доступной владельцу долговечной форме. Указать, временная ли это **debug**-сборка или готовая к последовательным обновлениям **release**-сборка; не путать их. Подготовить безопасный однократный шаг создания/сохранения release-ключа для первой постоянной установки.
9. Подготовить тестовые фикстуры без личных данных: пустая папка, `.md`, файл с кириллицей, разные расширения, файлы с одинаковыми именами; проверить работу при отказе доступа.
10. Первый APK должен запускаться **без фиктивных цифр памяти/демо-файлов**. Если доступ не дан — объяснить и показать путь предоставления разрешения, а не подменять реальные файлы примерами.

**Готово, когда:** Android-проект действительно компилируется, APK устанавливается после разрешений, основные кнопки работают на реальных файлах, персонализация сохраняется при перезапуске, пользовательские файлы не изменены неожиданно. Если проверить установку на телефоне невозможно — отметь `DEVICE_NOT_TESTED`, а не `PASS`.

### ЭТАП 2 — удобный видеоплеер

Media3, жесты ±10 с, минимум контролов, ручной fullscreen и ориентация, потокобезопасное открытие локальных URI; на устройстве проверить реальные разрешения/плавность, отдельно 4K60 на поддерживаемом кодеке.

### ЭТАП 3 — безопасные операции с файлами и архивы

Довести копирование/перенос/переименование/массовый выбор; аккуратное удаление/восстановление; ZIP → 7z → RAR и дополнительные архивы по мере подтверждённой стабильности. Приоритет — не потерять пользовательский файл.

### ЭТАП 4 — раздел приложений

Установленные приложения, извлечение доступных APK и split APK, экспорт/отправка, установка через штатный Android installer; проверить типовые APK и split-пакеты.

### ЭТАП 5 — дополнительные личные разделы и финальная доводка

Заметки, ссылки, избранное; **полноценный ручной экспорт и безопасное восстановление их данных вместе с настройками** (см. §7); затем, после проверки, опциональное автоматическое резервирование в выбранную пользователем папку. Юзабилити на реальном телефоне, исправление дефектов без изменения согласованного дизайна. Резервирование не должно блокировать сборку первого рабочего APK.

Этапы выполнять **последовательно, с самостоятельным продвижением после каждой исправной сборки**. Реальную проверку на vivo запрашивать только там, где без устройства нельзя подтвердить результат, кратким сообщением и **без требования пересылать новое ТЗ**. Если владелец не может тестировать сейчас, продолжай безопасную реализацию, фиксируя `DEVICE_NOT_TESTED`, а не останавливая всё из-за необязательных вопросов. Не работать над всеми пятью параллельно.

### Приёмочные сценарии для итоговой версии

- На vivo открывается главная, список настоящих файлов, «Новое» показывает свежие загрузки раньше старых при доступных метаданных; возвращение в приложение обновляет список.
- Пользователь меняет **иконку/расположение/состав** любой главной плитки и любой доступной нижней вкладки; настройки переживают перезапуск и обновление APK.
- Из «Новое» можно найти скачанный `.md`, посмотреть его или отправить через системное меню.
- Просмотр фото: перелистывание, zoom, сохранение пропорций и EXIF, никакой реакции на датчик поворота.
- Видео: воспроизведение, двойной тап слева/справа ровно −10/+10 с, отсутствие круглых дублирующих кнопок, ручной полноэкранный режим и возврат. Реальный 4K60 проверять на совместимом файле **и устройстве**.
- ZIP и другие реализованные архивы: просмотр/выборочная распаковка и проверка целостности; вредоносные пути/битые архивы безопасно отклоняются. Поддерживаемые форматы честно перечислены.
- Установленные приложения: доступный список, экспорт одиночного APK и, по возможности, split-набора, системная отправка; экспорт не притворяется бэкапом пользовательских данных.
- Опасные операции не теряют исходные данные при отказе/нехватке места/отмене; тесты на фикстурах.
- Заметки, ссылки, настройки: ручной экспорт, восстановление после проверки данных и подтверждения, отказоустойчивость; автокопирование только после целевых тестов.
- **Обновление поверх:** две последовательные сборки с одним `applicationId`, подписью и возрастающим `versionCode` сохраняют тестовые настройки и базу. Первая личная release-установка не должна зависеть от временного debug-ключа.
- Не использовать личные данные для тестов в облаке. Любой непроверенный на телефоне пункт маркировать `DEVICE_NOT_TESTED`.

## 10. Работа с лимитами Codex — ОБЯЗАТЕЛЬНО

Каждая рабочая сессия должна быть продолжима после сброса пятичасового лимита.

### Где храним состояние

- **`PROJECT_SPEC.md`** — копия ЭТОГО файла в корне нового репозитория; неизменный источник согласованных требований (менять только при новом пожелании владельца).
- **`PROJECT_STATUS.md`** — короткий, постоянно обновляемый журнал текущей реализации. Записывать только проверенные факты и известные ошибки.
- **Git** — коммиты законченных маленьких этапов. Создать новый проект, не использовать Git-репозитории других проектов.
- **Долговечное хранение:** если работа в облачном/временном окружении, одного локального коммита недостаточно. Разрешение на **один новый приватный репозиторий и push проекта уже включено в §0**; используй его, если доступны корректные полномочия. При недоступности GitHub подготовь для скачивания полный архив исходников с Git-историей (или безопасный Git bundle) и явно пометь `REMOTE_NOT_SAVED`. Никогда не заменяй подтверждение push фразой «сохранено». Не публикуй код публично.
- APK-сборка — отдельный артефакт для установки; её не обязательно коммитить в Git. Сохранять выпуск так, чтобы его можно было получить после окончания сессии; если подходит и разрешено — приватный GitHub Release или приложенный артефакт, **но никогда вместе с release-keystore и его паролем**.
- В `PROJECT_STATUS.md` сохраняй ссылки/идентификаторы артефактов, sha256, путь в репозитории, историю небольших WIP-изменений, и точный шаг для следующего агента. Не копируй сюда секреты и приватные файлы смартфона.
- **Передача Codex → Claude Code:** Claude использует **тот же новый приватный GitHub-репозиторий**, сначала читает `PROJECT_SPEC.md`, `PROJECT_STATUS.md`, `CHANGELOG.md`, Git-историю и воспроизводит минимальную необходимую сборку, затем продолжает со следующего незавершённого шага. Никакой отдельной версии ТЗ под Claude, миграции на другой язык или полной переписи архитектуры. Один агент пишет в рабочую ветку в один момент; без параллельных несовместимых изменений.

### Формат `PROJECT_STATUS.md`

```
# Статус разработки
- Последнее обновление (дата/время):
- Этап и его статус:
- Ветка / последний исправный Git-коммит:
- Сохранено локально / отправлено в удалённый репозиторий (точно):
- Реально готовые функции:
- Реально выполненные проверки (команды и результаты):
- APK: путь / debug или release / `applicationId`, `versionName`, `versionCode`, ABI, SHA-256 / установлен на телефоне? (YES/NO/NOT_TESTED):
- Незавершённые изменения / потенциальный WIP:
- Известные ошибки и риски для данных:
- Следующая конкретная задача:
- Как продолжить без повторных широких аудитов:
```

### Команда владельца «СОХРАНИТЬ» (когда осталось ~5–10% лимита)

> **СТОП: лимит Codex заканчивается.** Не начинай новые функции, не трать лимит на общий аудит. Проверь Git-статус и минимально необходимое для безопасной фиксации. Законченное и проверенное зафиксируй коммитом; незавершённый код не называй исправным и не смешивай с последней рабочей точкой. Если нужно, изолируй WIP в отдельной ветке/коммите с явной маркировкой, не затирая предыдущую рабочую версию. Обнови `PROJECT_STATUS.md` по согласованному шаблону. Сохрани проект долговечно разрешённым способом, проверь подтверждение push/передачи архива. Не добавляй секреты/ключи в Git. Назови последний исправный коммит, где сохранён код, и одно конкретное действие для следующей сессии. Новую задачу не начинай.

### Команда владельца «ПРОДОЛЖИТЬ» (после сброса лимита)

> **Продолжай тот же проект.** Открой `PROJECT_STATUS.md`, затем релевантный раздел `PROJECT_SPEC.md` и изучи текущий Git-статус. Убедись, что продолжение идёт из последней исправной точки: не принимай WIP за готовый результат, не перезаписывай изменения. Если среда новая, сначала восстанови разрешённый приватный репозиторий или ранее сохранённый архив. Выполняй **следующий незавершённый шаг**, без повторения готовой работы, ненужных аудитов и полного перепроектирования. После законченной части обнови статус и создай Git-коммит.

### Правила экономии лимита

- При ~5–10% оставшегося лимита владелец может отправить одно слово **«СОХРАНИТЬ»** или **«СТОП»**; агент исполняет соответствующий пункт выше. **Не полагайся на точную видимость оставшихся процентов внутри Codex:** выполняй обычные коммиты и push после каждого законченного этапа, чтобы не потерять работу при внезапной остановке.
- Когда лимит сброшен, владельцу достаточно написать **«ПРОДОЛЖИТЬ»** в том же проекте/новой сессии с доступом к тому же Git. Ни повторно отправлять MD, ни готовить новый стартовый промпт не нужно. Если это новая среда и проект не обнаружен — найти разрешённый приватный репозиторий/архив, не создавать вторую несвязанную копию.
- Сохраняй завершённые шаги регулярно **и до команды**, не только в самом конце.
- После сброса не нужно заново вставлять всё ТЗ: оно уже в репозитории под именем `PROJECT_SPEC.md`. Достаточно команды «ПРОДОЛЖИТЬ», если доступ к проекту восстановлен.
- Не рассчитывать на сохранение временного облачного рабочего каталога; только подтверждённое долговечное хранение.
- Если проблема мешает сборке, сначала исправь её; не добавляй новые функции поверх сломанной основы.

## 11. Рабочая среда, зависимости и право на остановку

- По умолчанию **Codex Cloud, не CONTROL**. Если Android SDK/Gradle отсутствуют, сначала используй официальные способы подготовки SDK в изолированной среде, избегая ручных опасных скриптов из неизвестных источников. Если установка инструментов в среде невозможна — честно передай исходники и команду сборки, не придумывая `.apk`.
- Сетевой доступ для скачивания build-зависимостей допускается **только в среде разработки**, это не повод вшивать сетевое разрешение в само приложение. Предпочитать официальные Google Maven / Maven Central и проверенные версии, проверять лицензии и активное сопровождение. Без неофициальных бинарников и лишних SDK.
- Gradle Wrapper/lockfile по уместности и инструкции воспроизводимой сборки (`./gradlew ...`) сохранить в репозитории. Секреты и неиспользуемые artefacts не коммитить. Для media/native codecs выбирать минимально нужные зависимости; отмечать реальные аппаратные ограничения.
- Если столкнулся с требованием доступа, которое **не может быть выдано одним этим файлом** (доступ к GitHub, защищённое хранение/выдача release-keystore, установка на личный смартфон), не запрашивай пароль/токен открытым текстом: выполни всю независимую часть задачи, дай одно конкретное безопасное действие владельцу и продолжи, когда оно станет возможным. Не выдавай блокер за готовый функционал.
- Не обещай «без ошибок»: документ задаёт проверки и критерии, но не заменяет реального тестирования. Не трогай другие проекты, production, DNS, оплату и облачные сервисы.

Коротко: **готово; проверено; APK/место хранения; незавершено; следующая задача.** Не выдавать архитектурный план за реализованное приложение. Не завышать оценку срока и не утверждать «всё безопасно» без испытаний.
